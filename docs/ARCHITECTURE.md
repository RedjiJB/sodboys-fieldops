# Architecture

D-Central-native successor to `fieldops-system` (v1) — built clean-slate per the approved plan (see the plan file this session was built from). v1 stays live for Sod Boys Ltd throughout this build; nothing here touches it.

## Backlog (not started — tracked for later prioritization)

**Mobile UI: data tables overflow on small viewports (found 2026-08-25, backlogged by request).** Every façade-backed page with a list (Equipment, Resources/Teams, Procurement, Payroll, Site Inventory, Field Time, Notifications, Vendors) hand-rolls its own `<table>` in a `overflow-x: auto` wrapper — confirmed live at 375px width on `/resources`: the table is 534px wide inside a 344px wrapper, so STATUS and the edit/delete action icons sit off-screen and require a horizontal scroll gesture inside the table to reach. The page itself never overflows the viewport (`document.documentElement.scrollWidth` stays at 375, matching the device width) — this isn't a broken-layout bug, it's a missing responsive treatment: nothing collapses these tables to a card list (or hides secondary columns) below a breakpoint. No shared `DataTable` component exists to fix this in one place — each of the ~8 pages would need its own pass. Real fix, not attempted yet: design and apply one responsive list pattern (most likely a card layout below `sm`, keeping the table above it) and roll it out page by page.

**Stale onboarding copy: Equipment's "Log readings" step (found 2026-08-25 while investigating the above).** The "How the fleet fits together" info card still tells users to "Record hour-meter, odometer and fuel readings to track real utilisation" — this describes the meter-reading modal removed earlier the same day (2026-08-24) because no backing POST-telemetry route exists. Same stale-guide bug class the "fix 5 stale guides" pass was built to catch, just missed because it shipped same-day as the removal. Needs the same treatment: update `equipmentGuide.ts`'s copy to drop the claim.

**`create_field_report` FK violation on `field_reports_created_by_fkey` (found 2026-09-08 via a real production alert sitting in the dashboard Inbox, root-caused 2026-09-11 while building the technical-walkthrough demo script).** `field_reports.created_by` is a FK to `users(id)` (dashboard users) by explicit migration-level design (`0040_field_reports.sql`'s own comment: "created_by references users, not crew_members — a field report is..."). But `src/mcp/tools/fieldReports.ts`'s `create_field_report` tool declares `createdBy` as `z.string().uuid().optional()` with no validation or documentation that it must specifically be a `users.id`, not a `crew_members.id`. When the WhatsApp bot resolves "owner" or "management" to a crew member's identity and passes that crew-member UUID through, the insert violates the FK constraint and the raw Postgres error reaches the alert pipeline verbatim — confirmed live in the Inbox as `"create_field_report fails server-side: FK violation on field_reports_created_by_fkey even with valid crew member IDs (tried owner + management)"`. Two real fixes needed, not yet attempted: (1) validate `createdBy` resolves to a real `users.id` before the insert and return a clean 422-equivalent MCP error instead of the raw FK violation, and (2) decide whether field reports should also be crew-member-attributable at all (if yes, needs a schema change — a nullable `created_by_crew_member_id` alongside the existing column, matching the dual-actor pattern already used elsewhere in this codebase per `docs/ARCHITECTURE.md`'s Phase 2 slice 3 notes on `purchase_orders.fulfilled_by`).

**Raw database/driver error text reaching user-facing alerts (found 2026-09-11, generalizing from the bug above).** The field-report incident is one confirmed instance of a broader pattern worth auditing system-wide: any code path where a caught DB/driver error's `.message` (a real constraint name, a raw SQL fragment) is passed through to `alerts.ts`/`notifications.ts` instead of being caught and re-worded into a clean, non-technical summary before it reaches a user-facing Inbox row. Not yet audited beyond the one confirmed case — needs a grep across every `raiseAlert`/notification call site for an un-sanitized `err.message`/`err.detail` interpolation.

**RESOLVED 2026-09-11 — Dashboard "Sites" widget excess whitespace.** Was a fixed 3-column CSS grid; switched to `repeat(auto-fill,minmax(260px,1fr))` so column count scales with real available width. `SiteCardsSection.tsx`.

**RESOLVED 2026-09-11 — "Locations & weather" panel truncation/cramped stats.** Added a `title` attribute to the truncated site name (hover recovers the full name); increased stat-line gap/line-height; widened the panel's fixed column from a stretchy fraction to a stable 380px so it doesn't balloon on wide screens. Also fixed a compounding issue found the same day: the whole widget shared a row with System Status/Inbox in a 2fr:1fr split that squeezed the map itself down to nothing at real site counts — moved the widget onto its own full-width row and widened the page's own max-width from 1024px to 1600px. `DashboardMapWeather.tsx`, `DashboardSitesPanel.tsx`, `ProjectWeather.tsx`, `HomePage.tsx`.

**RESOLVED 2026-09-11 — No general rate limiting on `/api/v1/*` routes.** New `src/facade/rateLimit.ts`: in-memory sliding-window limiter, two tiers (10/15min per-IP on login, independent of and complementary to `loginAttempts.ts`'s per-account lockout; 120/min general on everything else). Verified live: 11th rapid request returns 429 with `Retry-After`. Known, accepted limitation: per-process in-memory state, not shared across multiple façade processes — fine for this deployment's current single-process shape, would need a Postgres/Redis-backed counter if that ever changes.

**RESOLVED 2026-09-11 — No MFA on admin dashboard accounts.** TOTP (RFC 6238), verified against the standard's own published test vectors, no new backend dependency (Node's built-in `crypto` only). Two-step enrollment (`src/identity/totp.ts`, `users.ts`'s `startTotpEnrollment`/`confirmTotpEnrollment`) so a generated-but-unconfirmed secret can never silently start gating login. Frontend: a QR-code setup flow in Settings (`qrcode` npm package, client-side rendering of the backend's `otpauth://` URI) plus manual-key fallback. **A real bug found and fixed the same day**: the login page's own form was never updated to show a code field when the backend returned `requires_totp: true` — it just displayed the raw error, effectively locking out any account with MFA enabled. Fixed in `LoginPage.tsx`; verified live by grepping the deployed bundle for the fix, not just checking the build succeeded.

**Login page has no self-service "forgot password" flow (found 2026-09-08 via screenshot review; status: by design today, flagged for a real decision).** An admin resets a user's password directly via `resetUserPassword` (no current-password check, admin-only) — there is no email-link or SMS-based self-service reset anywhere in this system, consistent with there being no outbound-email infrastructure built yet. Not a bug, but worth an explicit "is this acceptable long-term" decision rather than leaving it silently unaddressed, since a locked-out staff user currently has no recourse without reaching an admin directly.

## Status (2026-08-24, OpenClaw/WhatsApp auth bridge, MSP monitoring, Site Cost Summary, a real production incident, and a security-audit pass)

A real `agent_identities` row was minted for OpenClaw (`did:web:id.sodboysltd.org:agents:openclaw-gateway`, tier 2, wildcard capability — deliberately excludes every tier-3/4 tool). Verified against the real production server, not a mock: a header-only `whoami` call resolved correctly with no `credentialJwt` argument; a `register_vehicle` (tier 3) call through the same credential was correctly denied. Caught a real bug along the way: `identity.ts` had its own local duplicate `credentialArg` (never imported from `shared.ts`), which would have broken `whoami`/`list_capabilities` — an agent's likely first calls — the moment this shipped.

New crew-facing MCP tools, all grounded in reading Sod Boys' actual WhatsApp chat archive (2181 messages) rather than guessed: `submit_spend_record` (tier 2, confirm-before-execute — closes the real gap where crew were emailing every receipt photo by hand because no crew-submittable spend record existed), `get_site_weather` (tier 0, reuses the already-`external_accepted` `weather_forecast` sovereignty decision), `submit_shift_extension` (v1 had this in its confirm-before-execute set, this rebuild never got an equivalent tool). Also added the location-sharing (`log_vehicle_location`/`log_location_share`) and vendor-lookup tools to OpenClaw's allow-list, which had been missed despite tool/equipment location tracking being the single most recurring pain point in the real chat history.

**MSP-grade self-monitoring wired to real checks.** The `systemHealth` MCP tools (`report_backup_status` etc.) existed as a well-designed ingestion point with nothing calling them. `ops/server/backup-db.sh` now reports via an `EXIT` trap; a new 15-minute heartbeat (`ops/server/ops-heartbeat.sh` + `dcentral-heartbeat.timer`) checks dashboard reachability/connectivity/disk space; `ops/server/external-uptime-check.sh` runs from the *separate* OpenClaw box every 5 minutes, checking the facade box's public endpoints from a genuinely external vantage point (the facade box's own heartbeat can't detect itself being totally unreachable). Auth: a new `ops-infra` agent identity with 5 separate narrowly-scoped tier-4 grants (one per specific `report_*` capability, not a wildcard — `npm run bootstrap:ops-infra-agent`). All server-side ops scripts are now version-controlled at `ops/server/` — they never were before this (created ad hoc via SSH earlier in the project).

**Site Cost Summary** (`src/domain/sites.ts`'s `getSiteCostSummary`/`setSiteBudget`, `GET/PATCH /api/v1/sites/:id/cost-summary`/`/budget`, `SiteCostPage.tsx` at `/5d`) — the real replacement for the "5D Cost" dead chip. Real spend from two sources: PO cost (`orders.site_id` join) and crew labour cost (reuses `fetchSessionsInRange`, filtered to sessions that visited the site, priced by each crew member's own hourly rate — no re-derivation of session logic). `budget`/`variance` are `null`, never `0`, when unset.

**A real, live production incident and recovery.** The facade box became unresponsive to SSH and HTTPS for over an hour after an on-box frontend build exhausted memory/swap (`tsc -b --max-old-space-size=9216` against a 954MB-RAM box). A soft reset got stuck in Oracle's own control plane for a long stretch (every retry rejected as a 409 conflict); it eventually self-resolved on its own — full memory recovery, all systemd services correctly auto-started on boot. Wrote `ops/DISASTER_RECOVERY.md` mid-incident: a full terminate-and-rebuild runbook usable by a human alone with no AI session, honest about the two things genuinely not preserved anywhere (the Caddyfile was never version-controlled; the Cloudflare Origin CA cert files only ever lived on the box). **Lesson, now load-bearing for every future deploy: never build the frontend on this box again** — build locally and ship the pre-built `dist/` via tar/scp, which is what actually got the site back to current state once it recovered.

**Backup restore tested for real, not just backup creation.** Spun up an isolated throwaway Postgres container, restored the latest nightly backup into it, verified real coherent data landed (not just a zero exit code). This had been flagged as an open gap for the whole project's history — closed.

**Security audit, substantially closed out.** `npm audit` clean (0 vulnerabilities, backend and frontend both). Git history scanned for secret patterns — none found; `.env` was never committed, `.gitignore` correctly excludes it. The notifications WebSocket "auth check" item turned out to be moot — confirmed via that route's own header comment that the endpoint was deliberately never built (frontend degrades to 30s polling by design). Chat assistant (`src/domain/chat.ts`) reviewed end-to-end for prompt-injection/infra-disclosure resistance: solid by construction (every tool read-only, so there's no dangerous action an injection could trigger regardless of conversational framing), bounded tool-call loop, errors never leak raw upstream provider text to the client. ## Status (2026-08-22, Task #156 slice H: field-time — a gap found before pruning)

**A real gap in the plan, not new scope**: the plan's per-module scope table listed field-time among the 8 kept modules, but its own sequencing section (slices A–G) never allocated a slice to it — confirmed by grepping the repo for any field-time façade route before starting the pruning pass and finding none. Built now, so pruning doesn't have to guess whether this route survives.

## Real bugs found and fixed (kept as a record across both identity-stack builds)

**In the current did:web/JWT-VC implementation:**

1. **`resolveDid` didn't catch a DNS/network failure**, only an HTTP-level "not ok" response — a nonexistent domain threw `TypeError: fetch failed` (`ENOTFOUND`) straight out of the function instead of returning `null` the way a 404 does. A resolution failure is exactly as legitimate an "unknown issuer" outcome as a 404; fixed by wrapping the fetch in a try/catch. Found by the very first test that exercised a genuinely non-existent domain, not by inspection.
2. **`registerCrewMember` built a crew identity across four separate, non-transactional inserts** (keypair → `PhoneBinding` VC → role capability grants → `crew_members` row). A failure partway through — a duplicate phone number, a crash, a killed process — left earlier steps already committed: a stranded DID with a real private key and signed credentials but no owning `crew_members` row. This is exactly what happened when earlier test runs got interrupted before reaching `afterAll`: the orphaned rows then collided with the next clean run's inserts on `nodes_did_key`/`crew_members_phone_key`/`keys_pkey` unique constraints, which also explained a 30x test-runtime slowdown (accumulated residue, not a logic bug). Fixed by wrapping the whole flow in one Postgres transaction — `generateAndStoreKeyPair` and `issueCapabilityGrant` both now accept an optional caller-owned `PoolClient` so they can join a larger transaction instead of always managing their own.

**In the earlier Veramo-based implementation** (retained for the record — these bugs are real, instructive, and were fixed in that code before it was replaced; they don't apply to the current implementation, which doesn't use `didwebvh-ts`, `Multikey`, or `@veramo/credential-jwt` at all):

2. `createDID`/`resolveDID`/`resolveDIDFromLog` in `didwebvh-ts` both required a working `verifier`, not just a `signer` — the original code only ever passed a signer, and would have thrown `"Verifier implementation is required"` on the first real resolution.
3. A `Multikey`-typed verification method's `publicKeyMultibase` needed a 2-byte multicodec prefix (`0xed01` for Ed25519) before multibase-encoding, not just the raw public key bytes — every DID created before the fix failed `didwebvh-ts`'s own log validation.
4. `@veramo/credential-jwt` 7.0.0's `verifyCredential` did not enforce JWT expiration on its own, `policies: { expirationDate: true }` notwithstanding — reproduced directly with a hand-built expired JWT-VC that still verified as `true`. Worth noting since it's a genuine point of comparison: `jose`'s `jwtVerify` in the current implementation enforces `exp` natively, confirmed by `test/vc.test.ts`'s expiration test, no application-level workaround needed this time.
5. Veramo's `CredentialPlugin` required an explicit JWT credential provider passed to its constructor — the zero-argument form didn't exist.

## Technology decisions

See the approved plan for the original reasoning; the DID/VC entries below supersede it per the explicit instruction to drop Veramo.

- **DID method**: `did:web` (not `did:webvh`) — chosen for simplicity over `did:webvh`'s hash-chained key-rotation history, by explicit instruction. Resolves over plain HTTPS, same trust model as the domain this system already runs behind. Used for **both** the node's own identity (bare-domain form) and every agent identity (path-based `did:web:<domain>:agents:<role>` sub-DIDs) — a single resolution mechanism for everything, rather than mixing `did:web`/`did:webvh` (node) with `did:key` (agents) the way the Veramo-based design did.
- **VC library**: none — a from-scratch JWT-VC implementation (`src/identity/vc.ts`). `jose` supplies only the underlying JWS/JWT mechanics (RFC 7515/7519: sign, verify, encode, decode) — it is not a DID/VC framework and has no opinion on DID methods or credential shapes; both of those are this project's own code.
- **Key management**: Node's native `crypto`/Web Crypto Ed25519 support (via `jose.generateKeyPair('EdDSA', { crv: 'Ed25519' })`), keys stored as JWKs in a new Postgres `keys` table (`src/db/migrations/0005_keys.sql`) — no external KMS, no Veramo key-manager abstraction.
- **MCP framework**: the official `@modelcontextprotocol` TypeScript SDK — `@modelcontextprotocol/server` (v2, current spec generation), `/client` for testing, `@modelcontextprotocol/node`'s `toNodeHandler` for the Streamable HTTP transport's plain-Node wiring. Unaffected by the identity-stack swap.
- **Capability layer**: a custom JWT-based capability-grant model (`CapabilityGrant` JWTs + a Postgres `capability_grants` index), rather than a full UCAN implementation — simpler to get genuinely correct in Phase 1, revisit UCAN specifically if delegation chains (not just direct node→agent grants) become necessary.
- **Backend**: Node/TypeScript (the MCP SDK, `jose`, and OpenClaw's plugin ecosystem are all TS-native).
- **Database**: Postgres, no separate graph DB. pgvector for the future knowledge/RAG layer is deferred to Phase 2+ (no domain knowledge base exists yet to index).
- **`zod` pinned to `^4.4.3`, not `3.x`** — this MCP SDK generation's `registerTool` expects Zod's native Standard Schema V1 support (specifically `jsonSchema` on the schema's `~standard` props), which only zod v4 implements. Passing a zod v3 schema fails both of `registerTool`'s overloads. (`did-resolver`'s version-pinning note from the Veramo era no longer applies — that package was removed entirely.)

## D-Central-native architecture layers

- **Node identity**: one bare-domain `did:web` per deployment (e.g. `did:web:id.dcentral-fieldops.local`) — root of trust issuing capability JWTs to agent DIDs.
- **Agent identity**: each distinct agent role gets its own path-based `did:web` sub-DID (e.g. `did:web:id.dcentral-fieldops.local:agents:crew-dispatch`), holding a capability JWT from the node DID stating its capability tier and capability set.
- **Crew members**: **reversed in Phase 2 slice 2** — every crew member holds a real, custodially-held `did:web:<domain>:crew:<uuid>`, with phone number demoted to a signed `PhoneBinding` VC bound to that DID rather than the primary identity. Role-based authority (`management`/`owner`) is a real, revocable `capability_grants` row backed by a signed VC, not a trusted `crew_members.role` string. See the Phase 2 slice 2 status section above.
- **Capability tiers**: 0 read-only, 1 propose/draft, 2 execute non-financial/non-schedule, 3 execute money/schedule/inventory, 4 admin/self-modifying. Every MCP tool declares its minimum tier; `src/mcp/middleware.ts`'s `requireCapability` enforces it per call.
- **Sovereignty-tiering policy**: `policy/sovereignty_tiers.yaml`, mirrored to Postgres by `npm run sync:policy`. **Reviewed 2026-08-21** — `reviewed_by`/`reviewed_at` are per-function now, not a single file-wide flag (the sync script previously stamped one top-level pair onto every row uniformly, which made "some reviewed, one still pending" structurally impossible even though that's the real state most of the time; fixed to match what the DB schema already supported). 4 of 5 functions reviewed and decided: LLM inference (`external_accepted` — provider set formalized as DeepSeek/Kimi/OpenAI/Gemini/Anthropic, the same chain v1 runs, carried forward deliberately), reverse-geocoding (`external_accepted` — the coordinate, not its formatted address, is the sensitive part, and it's already at rest in this system's own DB regardless), weather (`external_accepted` — no crew-identifying data in a location/date query), and federation transport (`self_hosted_required` by definition, not really a judgment call but marked reviewed for completeness). **`embedding_generation` stays genuinely `external_pending`** — not deferred out of caution, but because the real blocker (a local-embedding-model benchmark on the actual target hardware) doesn't exist yet; see "Open decisions" below.
- **MCP as universal surface**: every capability, D-Central-layer and future domain-layer alike, is an MCP tool. Capability checks are argument-based (`credentialJwt` passed in the tool call itself), not HTTP-bearer-only, specifically because it has to work identically over stdio, which has no HTTP layer to carry a bearer token.
- **Federation, genuinely single-node**: `src/federation/FederationTransport.ts` is a real interface with one real (not stubbed-to-throw) loopback implementation. `federation_peers`/`federation_proposals`/`federation_votes`/`dcredit_ledger` tables exist and function correctly at N=1 (a quorum-of-one vote is a degenerate but real instance of the same code path a second node would use) — a second node later means a new `FederationTransport` implementation and new rows, not a schema change.

## Frontend

Decided by explicit instruction, not the default this repo would otherwise have arrived at: the dashboard reuses [OpenConstructionERP](https://github.com/datadrivenconstruction/OpenConstructionERP)'s frontend rather than being built from scratch. Vendored as a git submodule at `vendor/openconstructionerp` (the *whole* upstream monorepo — it has its own `backend/`, `modules/`, `services/`, etc. alongside `frontend/`; only the `frontend/` subdirectory is actually used here). Submodule, not a squashed copy, specifically so its own `LICENSE`/`NOTICE`/`CONTRIBUTORS.md` stay intact and separately trackable against upstream — that matters for the point below, not just for pulling updates.

**License, stated plainly since it has real teeth**: OpenConstructionERP is AGPL-3.0. Confirmed and accepted directly, not a default — see the instruction that added this. The concrete mechanism, so "accepted" means the actual thing and not a vaguer one: AGPL-3.0's network-use clause (§13) means that if this system is modified and made available to users over a network (which a live FieldOps deployment is, by definition), the complete corresponding source of the *combined work* must be offered to every user who interacts with it — not just to someone who receives a distributed copy. Depending on how tightly the frontend and this system's own backend end up integrated (a separate REST API consumed over HTTP is the safer shape; statically linking or bundling code together is not), this plausibly extends the AGPL obligation to more than just `vendor/openconstructionerp/frontend/`'s own files. Two things worth knowing, found while vendoring, not previously flagged: OpenConstructionERP ships a `COMMERCIAL-LICENSE.md` — a paid non-AGPL license option exists from the upstream project if the AGPL obligation ever conflicts with the licensing/franchise business direction discussed for this system (see the wider planning history); and the vendored repo is a substantially more capable frontend than earlier design research assumed — React 18 + TypeScript + Vite, but also TanStack Query, AG Grid, MapLibre GL, Cesium (3D/geospatial), react-i18next, react-router-dom v7, not the smaller React/Tailwind/Recharts/Zustand stack previously described.

**Not yet done, real follow-up work**: actually wiring `vendor/openconstructionerp/frontend/` to this system's backend. It's a large, general-purpose construction-ERP UI (project/estimating/BIM/procurement workflows) that needs real adaptation to FieldOps' actual domain (dispatch, crew, sites, checkouts, exceptions) — not just an API base URL pointed at a new backend. Concretely: a thin REST façade needs to sit in front of the MCP tool implementations for the browser to call (see decision #4 above), the nav/routing needs cutting down to FieldOps' actual screens, and auth needs a real design (this system's capability-VC model is agent-to-agent, not a browser session model — the dashboard needs its own login story, not a repurposed agent DID). None of this is started.
